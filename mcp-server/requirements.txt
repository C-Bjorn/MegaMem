# this server. Ceiling excludes the entire 2.x line until the v2 low-level API migration
# (tracked separately, not a hotfix). See megamem_mcp_server.py's startup version guard
# for the runtime enforcement of this same range.

# Day79.02 Task 4: pin transitive `redis` below 8.1.0. `redis` is not a graphiti-core
# dependency at all - it arrives transitively via the `falkordb` extra's own dependency
# (falkordb-py 1.6.2 declares only `redis>=7.1.0`, no upper bound). redis-py 8.1.0 added an
# HImportRegistry feature whose async ConnectionPool auto-injects a `himport_registry` kwarg
# into `connection_kwargs`. falkordb-py's cluster-detection probe (`Is_Cluster()`) copies
# those async pool kwargs wholesale into a SYNCHRONOUS `redis.Redis(**kwargs)` constructor
# call to check `redis_mode` - the sync client's `__init__` does not accept
# `himport_registry`, so ANY `FalkorDriver(...)` construction raises
# `TypeError: Redis.__init__() got an unexpected keyword argument 'himport_registry'`
# immediately, before any query runs. Bisected: redis==8.0.0 constructs cleanly;
# redis==8.1.0 fails 100% of the time. This is unrelated to FalkorDB's own server-side
# "requires Redis 8.0.0+" requirement in its docs - that refers to the FalkorDB/Redis
# SERVER version, not this redis PYTHON CLIENT package; the two are different artifacts
# with unrelated version lines. Confirmed this is a real shipped-product bug, not a
# repo-venv quirk: a fresh `pip install -r requirements.txt` today resolves redis==8.1.0
# with no conflict (a "clean" resolution that is nonetheless runtime-broken for FalkorDB).
# graphiti-core's own upstream uv.lock (e:/GIT/LOCAL/graphiti/uv.lock) pins redis==7.1.0,
# well under this boundary - matches this pin's intent. Removable once falkordb-py fixes
# Is_Cluster() to build a redis-version-safe kwargs dict (bug not yet filed upstream as of
# 2026-08-12), or once redis-py stops auto-injecting async-only kwargs into shared
# connection_kwargs.
redis>=7.1.0,<8.1.0
